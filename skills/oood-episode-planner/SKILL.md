# OOOD episode planner

Read the live repository's AGENTS.md and current context/decisions/open questions. Locate the project from the working directory or `/Users/je/oood`; if unavailable, use [show context](references/show-context.md). Read [editorial direction](references/editorial-direction.md) and [brand guide](references/brand-guide.md). Live host instructions and repo state override bundled snapshots. Do not assume you can edit or read a remote ChatGPT Project.

The show succeeds when people want more time with **Josh and Mary together**, understand the idea, and can try something. A tidy lesson alone is insufficient. Preserve competence and agency for both hosts. They can tease themselves and each other affectionately; the viewer is never the butt of the joke. Avoid scripted marital conflict, a teacher/sidekick pattern, fabricated anecdotes, and forced punchlines.

## Build the episode

- Infer the requested episode/topic and stage from context. Ask only for information that changes the plan; keep progressing on independent work. Recording order and release order are different.
- Choose a recognizable question plus a human tension: different preferences, an expectation that met reality, a small challenge, or a surprising actual result. State the one thing the audience will leave knowing or doing.
- Pull real, approved experiences from source material. Mark unconfirmed story slots as prompts, never completed anecdotes. For research, keep a claim-level source pack with publisher, date, URL, access date, supported claim, and limits.
- Build a short chronological outline: entertaining opening, plain promise, explanation through an example, genuine host reactions, a miss or limit, and one action. The number and length of beats should serve the episode, not a fixed template.
- Give each host something to explain, evaluate, and challenge. Use their real differences; don't invent fixed personality stereotypes. Protect setup → response → laugh/callback when it earns its time.
- Design optional moments for spontaneity: predict before revealing an actual output, compare two real choices, let each host defend a preference. Label these as formats to try, not dialogue that supposedly happened.
- Explain jargon in the sentence where it first matters. Introduce a person/tool/custom skill before callbacks. Motivate transitions with the problem the next section solves.
- Visuals support the conversation. Until hosts choose otherwise, propose options that keep the core explanation complete through audio. Any permanent screen-share or recurring-segment choice stays open.
- Keep camera notes concise. Offer optional opener/bridge phrasing, not a full memorized dialogue unless requested. Read the outline aloud for natural handoffs.

## Deliver

For a new episode, create the brief from the live `templates/EPISODE_BRIEF_TEMPLATE.md`, the research/claim notes required, and a concise chronological recording cue sheet. For reshoots, add a prioritized feedback list tied to actual source/export timestamps and distinguish transcript-based findings from audiovisual observations. Include what to preserve, not just cuts.

Add a “why someone watches us” check: does this contain a specific reaction, a glimpse of the relationship, and both hosts' judgment? These are editorial questions, not mandatory artificial quotas. Never strip out the relationship merely to hit an arbitrary runtime.

Mark plans/scripts draft until approved. Update current context and durable decisions only for direct host choices, not your suggested format. Leave recording/publication unconfirmed until evidence exists. Return usable files and a short summary of the highest-value choices.
